## Installed Versus Selected

**INSTALLED:** ordinary N=1 uses a current Component Analyst case, exact
deterministic binding, direct RunKernel component admission,
ComponentCoverage, Sufficiency, FAP, and Author. Component D-prime has no
ordinary component producer or consumer.

For genuine N>=2 work, the installed bounded path still uses Cross-Component
Analyst followed by a separate synthesis D-prime model call before RunKernel
synthesis admission.

**SELECTED TARGET:** retain one strong semantic owner for each kind of meaning.
Component Analyst owns one-component meaning and self-audit. Cross owns genuine
cross-component relationship meaning and self-audit. The remaining ordinary
synthesis D-prime call is selected for retirement only after focused PRODUCT
convergence proves its differentiated work can be absorbed without weakening
quality. Scrutineer remains the sole separate semantic reviewer when mode/risk
policy warrants one.

Installed behavior is not permanent architecture, and selected architecture is
not installed until code changes merge.

## Product Boundary

AnalystOS is the post-SearchOS semantic subsystem. It owns evidence-relative
case building, relationship analysis, optional recovery/Specialist consumption,
challenge, and handoff to canonical admission and whole-run readiness.

It is not the kernel, provider router, graph mutator, Sufficiency reducer, FAP,
or Author.

The durable ordinary chain is:

```text
SearchOS lawful handoff
-> Component Analyst case + self-audit
-> RunKernel exact binding/admission
-> ComponentCoverage
-> Cross only for genuine N>=2 relationship meaning
-> optional Scrutineer/revision when policy selects it
-> RunKernel graph/synthesis admission
-> Sufficiency computes whole-run readiness
-> FAP packages
-> Author writes
```

## Component Analyst

Component Analyst owns one component's meaning:

- what the bounded evidence establishes and does not establish;
- a supported claim or lawful no-claim posture;
- applicability, source role, scope, version, jurisdiction, population, and
  temporal meaning;
- caveats, nonclaims, contradictions, alternatives, and uncertainty;
- missing evidentiary premise or calculation need; and
- self-audit against overreach.

Its output is a semantic proposal until RunKernel admits it. It must not invent
runtime IDs, canonical refs, digests, revisions, route authority, or final prose.

Self-audit is part of producing a defensible case, not a second synonymous vote.

## RunKernel Admission

RunKernel owns exact mechanics:

- current request/run/action and accepted-contract identity;
- exact component, evidence, observation, Coverage, and Specialist refs;
- schema, digest, revision, currentness, stale/foreign, and replay checks;
- graph legality and exactly-once reduction; and
- canonical mutation.

RunKernel may reject malformed or impossible proposals. It does not reinterpret
natural-language support or manufacture semantic output.

## ComponentCoverage And Sufficiency

ComponentCoverage records whether one requested component is ready from current
admitted semantic state and lawful evidence custody.

Sufficiency is a deterministic whole-run policy reduction over canonical state.
It decides no new meaning. It computes whether required answer targets and
source obligations are fulfilled, whether blocking conflicts/unknowns remain,
and whether the final posture is direct, caveated, partial, insufficient, or
blocked.

A valid RunKernel state may still be insufficient: everything known can be
lawfully admitted while the user-requested answer remains incomplete.

## N=1 Folding

N=1 is intentionally simple:

```text
SearchOS handoff
-> one Component Analyst case + self-audit
-> RunKernel admission
-> ComponentCoverage
-> Sufficiency
-> FAP
-> Author
```

Ordinary N=1 does not schedule Cross, component D-prime, synthesis D-prime,
Scrutineer, or Specialist unless the query genuinely requires their distinct
responsibility.

## Cross-Component Analyst

Cross runs only for genuine N>=2 relationship meaning such as comparison,
contradiction, dependency, synthesis, or a cross-component calculation need.

It may produce zero to many synthesis proposals. Zero is lawful. Cross owns the
relationship's meaning, caveats, nonclaims, and self-audit. Code owns exact
upstream refs, graph identity, topology, depth ceilings, currentness, and
admission.

The currently installed synthesis D-prime reviews Cross proposals before
admission. The selected target eventually folds useful synthesis scrutiny into
Cross self-audit plus risk-scaled Scrutineer, but does not remove deterministic
graph validation or RunKernel admission.

## Specialist And Recovery

A source-stated literal is ordinary direct-source evidence. It does not need
Specialist merely because it contains digits.

When a component or synthesis requires a genuinely new deterministic result:

```text
semantic owner identifies exact need
-> code validates/binds request
-> Specialist executes bounded work
-> semantic owner consumes and interprets result
-> RunKernel admits exact current lineage
```

Specialist execution success alone is not support and cannot bypass the
semantic owner.

When Analyst identifies a missing premise, authorized SearchOS recovery may
retrieve new evidence. Custody returns to Analyst for resumed analysis before
admission. SearchOS recovery does not author support.

## Scrutineer And Mode Direction

Scrutineer is the sole separate semantic reviewer in the selected target. It
asks what is wrong, omitted, contradicted, fragile, misleading, or insufficient.
It challenges; it does not replace the case, retrieve evidence, admit state, or
write final prose.

Selected mode direction:

| Mode | Posture |
| --- | --- |
| Fast | No routine Scrutineer; qualify, block, or escalate rather than launch a review campaign. |
| Balanced | Risk-triggered Scrutineer for material contradiction, dependency, high-stakes quantitative posture, or fragile synthesis; at most one revision. |
| Deep | Whole-case Scrutineer with at most one revision/adjudication cycle. |

These are selected policy directions; exact installed activation remains owned
by current code and focused tests.

## Downstream Boundary

FAP receives only RunKernel-admitted state that Sufficiency authorizes. It is
semantically stupid and mechanically strict: it packages claims, Analyst
context, caveats/nonclaims, citations, and bounded evidence without deciding
what prose means.

Author is the final semantic actor. After Author, mechanics only.

Direct-source numbers are ordinary admitted claim content. Derived/calculated
results retain exact Specialist authority. Neither FAP nor post-Author code may
become a second Analyst by reparsing prose.

## Architecture Locks

Do not reintroduce without explicit maintainer decision:

- routine component D-prime consumption;
- Cross or synthesis ceremony for N=1;
- FAP fingerprints, token overlap, literal-role heuristics, or proposition
  matching as PRODUCT authority;
- telemetry/helper source-class authority;
- post-Author semantic verification or retry; or
- a second semantic vote that adds no differentiated cognitive work.
