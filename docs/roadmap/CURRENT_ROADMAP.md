## Active Decision Gate: REPRESENTATIVE MULTI-COMPONENT PRODUCT OBSERVATION

The next product-moving step is one bounded ordinary query that genuinely
requires multiple factual components and a relationship such as comparison,
contradiction, dependency, or synthesis.

The observation should answer:

```text
Can the installed ordinary product produce multiple admitted Component Analyst
cases, invoke Cross only for real relationship work, reach whole-run
Sufficiency, and deliver a supported cited Author answer without forced
ceremony?
```

### Success posture

```text
multiple Component Analyst cases admitted
required components ready
Cross invoked only when the request needs relationship meaning
0..N synthesis proposals accepted lawfully
no forced synthesis
Sufficiency computes a defensible whole-answer posture
FAP packages current admitted material
Author produces a supported cited answer
```

### Failure posture

If the observation fails:

1. identify the first real owner from sanitized PRODUCT evidence;
2. distinguish a mechanical transport/integrity defect from an architecture or
   semantic-policy decision;
3. repair one coherent causal cluster only when licensed;
4. prove it offline;
5. spend another PRODUCT run only under an explicit convergence budget.

Do not build more observability or another evaluator before the product exposes
a concrete blind spot.

a focused convergence phase show that Cross self-audit plus mechanical admission
can replace its useful differentiated work. Do not claim that retirement is
installed before code changes land.

## After The First Multi-Component Observation

Use the result to choose one branch:

### Product success

Move to a small diverse ordinary-query cohort rather than polishing the same
query. Candidate coverage:

```text
simple nonnumeric fact
mutable present-tense fact
historical old-but-valid fact
reputable-secondary fact
source-bound calculation requiring Specialist
unsupported or ambiguous case that should not overclaim
```

Keep the cohort small enough to influence architecture decisions. Do not create
benchmark bureaucracy.

### Focused mechanical defect

Repair the first owner while preserving:

```text
MODEL AUTHORS MEANING.
CODE AUTHORS MECHANICS.
```

Do not move semantic interpretation into FAP, Sufficiency, or deterministic
parsers.

### Architecture stop

Stop when the fix would require a new semantic truth system, a protected policy
change, or canonical information that no installed owner currently produces.
Make that product decision explicitly before another live run.

## Product Doctrine

```text
representative ordinary query
-> ordinary ScryRaven
-> correct supported cited answer or honest blocker
```

Correctness machinery must earn complexity through answer quality, safety,
privacy, or cost control. Internal proof completeness is not itself a product
goal.

Prefer:

```text
better Analyst judgment + better bounded evidence context
-> simpler Sufficiency and FAP mechanics
-> capable Author
```

rather than more deterministic interpretation between Analyst and Author.
